Development & CI

How this project is tested, built, and released.

Local setup

npm install
npm start

Opens http://localhost:4173. Requires Node.js 24+ (the library index uses the built-in node:sqlite module, unavailable on older Node).

Tests

npm test

Node's built-in test runner (node --test), no separate test framework. The one write path into a real Music.app library (restore) is tested against a fake musicLibrary implementation (test/fixtures/fakeMusicLibrary.js, swapped in via PLE_TEST_MUSIC_LIBRARY) rather than a live app, since that can't run in CI.

Continuous integration

.github/workflows/ci.yml runs on every push and PR to main, on a macos-latest runner (needed to compile the Swift native app, and to genuinely represent the target platform):

  1. Install Node 24 and ffmpeg (the M4A tag-writer's test shells out to it directly)
  2. Install dependencies (npm ci) and run the full test suite
  3. Read the version from package.json
  4. Build the native macOS app (macapp/build.sh)
  5. Upload it as a build artifact, named Playlist Exporter-vX.Y.Z

The Test and build macOS app check is a required status check on main — a PR can't merge with failing tests or a broken build.

Versioning policy

package.json's version is the single source of truth (plain semver). Bump it in the same commit/PR as the change it belongs to — everything else (web UI, native app's Info.plist, CI artifact name) picks it up automatically. There's no enforced bump-on-every-PR check; for a single-developer local tool that's more process than it's worth.

Branch protection

main requires the CI status check to pass before merging, and blocks force-pushes and deletions. (GitHub's branch protection isn't available on a private repo without a paid plan — this repo is public specifically to enable it.)
