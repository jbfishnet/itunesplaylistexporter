Search & Enrichment

A searchable offline index of a whole NAS music archive, independent of Music.app.

Indexing

On startup, and then every hour, the app walks the configured library root(s) (PLE_LIBRARY_ROOT) directly on disk — no Music.app involved — reading embedded tags (ID3/MP4/FLAC/etc.) from every audio file it finds. Rescans are incremental: only new or changed files are re-read, so only the first scan of a large archive is slow. If a NAS root isn't mounted when a scan runs, the existing index is left untouched rather than wiped.

The index lives in a local SQLite database (with FTS5 for full-text search), stored per-install under ~/Library/Application Support/Playlist Exporter/ for the native app.

Search

Full-text search across title/artist/album/genre, and always the filename/folder too — so even a completely untagged file is still findable.

Search results can be previewed in the app. Starting a preview first pauses Music.app if it is currently playing. To add a result, select a Music.app playlist; after two seconds the file is imported and added automatically. The app verifies the new playlist entry with Music.app, then refreshes its playlist count and track list. DRM-protected files can't be previewed or added this way. Adding uses macOS Automation permission for Music.app; preview playback does not pause browser radio or playback in other apps.

Metadata enrichment

Files with missing or placeholder tags (no artist, no genre, an album literally called "Unknown Album", etc.) are queued for a background lookup against Apple's iTunes Search API — no signup or API key needed. This runs slowly and continuously (roughly one lookup every 1.75s) so it never hammers Apple's servers; a large backlog just drains gradually in the background. Well-tagged files are never looked up at all.

A match is written back into the file's own tags on disk — MP3 via ID3, M4A via a lossless ffmpeg remux — never overwriting a field that already has a real value, only filling in what was actually missing or a recognized placeholder. That's what makes it permanent: a reindex never needs to re-enrich the same file twice, because the fix lives in the file, not just the database.

This wasn't always reliable. A real bug meant a file whose only gap was a placeholder album (e.g. literally "Unknown Album") never actually got fixed on disk, because the tag-writer's "is this field empty" check didn't recognize placeholder text the same way the scanner's "does this need enrichment" check did — so the same ~3,700 files kept getting re-flagged on every scan. Both checks now share one definition (src/metadataPlaceholders.js) so they can't drift apart again.

Protected files and formats without a writer (anything but MP3/M4A) only get the result in the index, not the file. If the on-disk write itself fails (ffmpeg missing, a permissions error, a NAS hiccup) while the lookup still succeeded, that's tracked separately, surfaced in the Queue tab, and automatically retried every 5 minutes without repeating the API call — or immediately via a "Retry failed writes" button.

Not Found

Files whose iTunes lookup found nothing plausible are terminal ("not_found") rather than retried forever — they're listed in the Not Found tab, and can be requeued in bulk after a matching-logic improvement ships.

When text search finds no plausible result, the enrichment queue can also fingerprint the audio locally with Chromaprint and query AcoustID. The native app stores an optional free AcoustID application key in the user's Application Support folder with account-only file permissions, outside the app bundle so it survives app updates; only the fingerprint and duration are sent to AcoustID, not the audio file. The Configuration page can test the key using a synthetic silence fingerprint, and warns when the key is missing or rejected. AcoustID's catalog is community-built and is not as broad as Shazam's. Without a key, this fallback is disabled. A single Not Found track can be selected and retried immediately after configuring the key.
